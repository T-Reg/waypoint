# Identity & Tokens

Part of the [design](design.md). Covers customer and admin tokens, the identity tokens sent to upstreams, and the JWKS endpoint. Test cases are in [testing.md](testing.md#identity-token--jwks).

## 1. Authentication: customer and admin tokens

**Token types** (admin tokens, a third type with their own key, are described in [design.md §5](design.md#5-dynamic-routing)):

| | Customer token | Identity token |
|---|---|---|
| Purpose | Caller proves who it is to the gateway | Gateway tells the upstream who the verified caller is |
| Sent as | `Authorization: Bearer …` (client → gateway) | `X-Gateway-Identity` (gateway → upstream) |
| Signed by | Token issuer (private key never on the gateway) | Gateway (its own key) |
| Verified by | Gateway (issuer's public key) | Upstreams (gateway's JWKS) |
| `aud` | The gateway | One specific upstream (`route.audience`) |
| Lifetime | ~15 min | 60 s |
| Details | This section | §2 |

Keeping the key pairs separate means a compromised gateway can mint identity tokens but **not** customer tokens.

- **Issuance:** a `token-cli` holds the issuer's **private key** and signs customer tokens. The gateway is configured with the **public key** only.
  - **Where the issuer lives:** it's a separate CLI entry point in this repo, not part of the gateway process. An operator runs it by hand, e.g. `token-cli issue --tenant acme --sub web-app --scope "weather:read" --ttl 15m`.
  - **Keys:** the private key is a file kept outside the repo (a dev key is generated by a script and git-ignored). The gateway only reads the public key, via config.
- **Stand-in: the issuer CLI.** Given limited time, the CLI is a deliberate stop-gap, not the intended design. It produces tokens in the same shape a real issuer would.
  - **Current gap:** manual issuance, a file-based key, no revocation.
  - **Possible future improvement:** build or adopt a **token service** (an OAuth 2.0 authorization server such as Keycloak, Auth0 or Okta, or one built in-house). It would provide:
  - A client-credentials endpoint (`POST /oauth/token`) so tenants get tokens self-service instead of by hand from an operator.
  - Client registration per tenant, with client secrets or `private_key_jwt`.
  - Revocation (client disablement plus a `jti` denylist) and an introspection endpoint.
  - A signing key held in a KMS/HSM, with `kid`-based rotation published via JWKS.
  - Audit of every issuance.

  The gateway would not change, except to fetch the issuer's JWKS instead of reading a static public key.
- **Claims:**

  | Claim | Meaning |
  |---|---|
  | `iss` | Issuer, checked against config |
  | `aud` | Must equal the gateway's audience |
  | `sub` | Caller (client) identifier |
  | `tid` | Tenant ID, used for all policy |
  | `scope` | Space-separated scopes |
  | `iat`, `nbf`, `exp` | Short TTL (e.g. 15 min) |
  | `jti` | Unique token ID (enables a future denylist) |

- **Validation:**
  - The algorithm is pinned to the fully-specified `alg: Ed25519` ([RFC 9864](https://www.rfc-editor.org/rfc/rfc9864.html)). `none`, HS*, the deprecated polymorphic `EdDSA` and anything else are rejected. Nimbus 10.10 supports `Ed25519`, so no fallback is needed.
  - Keys come only from configuration (an inline JWK/JWK set or a file). `jku`, `x5u` and embedded `jwk` headers are ignored. A `kid` selects among configured keys, so the issuer key can rotate.
  - The `typ` header must match the token type (`customer+jwt`, `admin+jwt`, `identity+jwt`), per [RFC 8725 §3.11](https://datatracker.ietf.org/doc/html/rfc8725#section-3.11).
  - `aud` must be a single value.
  - Signature, `iss`, `aud`, `exp` and `nbf` are all required, with ±30s clock skew allowed.
  - The `tid` claim must be present.
  - The tenant must exist in the tenant store, and unknown tenants are rejected with 401.
  - All of this follows [RFC 8725](https://datatracker.ietf.org/doc/html/rfc8725).
- **Interface:** `Authenticator.authenticate(request) → TenantIdentity | AuthFailure`. An API-key scheme could plug in later.
- **Revocation:** there's no per-token revocation before `exp`.
  - Setting a tenant's `disabled` flag (or deleting the tenant) revokes all of its tokens within the propagation bound ([multi-instance.md](multi-instance.md)), because unknown or disabled tenants get 401.
  - Mitigations for individual tokens: a short TTL, and an optional `jti` denylist.

## 2. Identity propagation to upstreams

**Problem: the confused deputy.**
- A plain `X-Gateway-Tenant-Id` header is unverifiable. Anything on the internal network could send it.
- A downstream service calling another service has nothing to prove which customer the work is for.
- Scopes alone also aren't enough. They say *what kind* of action is allowed, not *which object*.
- Object-level authorization ("does Acme own document 123?") must be done by the service that owns the data ([OWASP API1: BOLA](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)). That service needs a verifiable identity to do it.

**Design: a gateway-signed identity token** (Netflix "Passport" pattern; [OWASP Microservices Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Microservices_Security_Cheat_Sheet.html)).
- After all policy checks pass, the gateway mints a short-lived JWT and sends it as `X-Gateway-Identity`.
- It's signed with the **gateway's own Ed25519 key**, which is separate from the customer-token issuer's key.

  | Claim | Value |
  |---|---|
  | `iss` | The gateway |
  | `aud` | `route.audience`, so it's bound to one upstream and can't be replayed to another service |
  | `sub`, `tid` | The caller and tenant from the verified customer token |
  | `scope` | The caller's granted scopes **filtered by `route.forwardScopes`** (e.g. `weather:*`), so the weather service never learns about `billing:write` |
  | `iat`, `exp` | `exp` = now + 60s |
  | `jti` | Unique ID |
  | `rid` | Request ID, for tracing |

- **Why not forward the customer's token:**
  - Its `aud` is the gateway.
  - It lives 15 minutes.
  - It would be accepted by any service that trusts the issuer.
  - It also leaks a customer credential into internal logs.
  - So raw tokens stay at the edge.
- **Key publishing and rotation (in scope, fully tested):** see "JWKS endpoint" below.
- **What upstreams do:**
  1. Verify the signature using the JWKS.
  2. Check `iss`, that `aud` equals their own audience, and `exp`.
  3. Use `tid`/`sub` for object-level authorization.
  4. Reject requests that lack the header.
- **Interface:** `IdentityTokenMinter.mint(TenantIdentity, Route, requestId) → String`.
- **Current gap / possible future improvement:**
  - Today the gateway operator configures `forwardScopes` per route.
  - Ideally each upstream would **declare which scopes it needs** to fulfill specific requests (e.g. a published per-endpoint scope manifest the gateway reads), so the token carries exactly what that request needs.
  - That's more config and more moving parts, so it's deferred.

### JWKS endpoint (in scope)

**Why:** upstreams need the gateway's public key to verify `X-Gateway-Identity`. Publishing it as a JWKS ([RFC 7517](https://datatracker.ietf.org/doc/html/rfc7517)) lets us rotate keys without reconfiguring every upstream.

**Behavior:**
- **Endpoint:** `GET /.well-known/jwks.json` on the **management listener only** ([design.md §3](design.md#3-request-pipeline)). It is not served on the public or admin listener.
  - No credential, because public keys aren't secret.
  - Response type `application/jwk-set+json`, with `Cache-Control: max-age=300`.
- **Contents:** only public parameters (`kty=OKP`, `crv=Ed25519`, `x`, `kid`, `alg=Ed25519`, `use=sig`). The private component `d` must never appear. The `kid` is the key's RFC 7638 thumbprint.
- **Key lifecycle:**
  - Each instance generates its own Ed25519 key pair **in memory at startup**. The private key is never written to disk or to the DB, so there's no key file or row to leak.
  - The instance registers its **public** key in `gateway_keys` ([multi-instance.md](multi-instance.md)) and heartbeats it. The insert and a `NOTIFY key:<kid>` run in one statement, so peers refresh their key set within milliseconds of the commit rather than on their next poll.
  - **Every instance's JWKS serves all live public keys from `gateway_keys`**, so a token minted by any instance verifies via the JWKS fetched from any instance behind the LB.
  - The JWKS is served from an in-memory, last-known-good key set that always includes the instance's own keys, and it's refreshed from the DB when available. A DB outage therefore doesn't break verification.
  - Other instances' keys aren't expired while the reading instance itself can't reach the DB.
  - **Staleness and readiness (refined during implementation):** peers drop a key whose instance hasn't heartbeated for `key-stale-after` (default 10 min). An instance goes **not-ready** once its own heartbeat has failed for `key-stale-after − token-ttl − clock-skew` (default 8.5 min). So every token it minted while ready expires before any peer stops publishing its key (R20).
    - A crashed instance's public key lingering is harmless, because its private key died with the process. A long staleness window therefore costs nothing, and it buys tolerance of DB outages.
    - Trade-off: an instance can't tell "I am partitioned" from "the DB is down for everyone". A **total** DB outage longer than ~8.5 min (defaults) therefore makes every instance not-ready. Raise `key-stale-after` to widen that window.
  - A restart produces a new `kid`. Upstreams handle that by refetching when they see an unknown `kid`.
  - **Remaining gap at startup:** a new instance signs as soon as it's ready, with no grace period. Its key reaches peers' JWKS via NOTIFY within milliseconds, well inside an LB's health-check rise time (HAProxy `rise 2`, `inter 1s`). If that NOTIFY is lost, peers learn the key on their next poll (≤ `poll-interval`).
- **Rotation:** `POST /admin/keys/rotate` (admin JWT with `admin:keys` required) bumps `key_rotation.generation` and sends `NOTIFY`. Every instance rotates once per generation, whichever path (the request itself, NOTIFY or the poll) sees it first.
  1. Generate a new key, register its public half (which notifies peers) and publish it alongside the current one.
  2. Keep signing with the current key for `gateway.identity.key-publish-grace` (default 10s, equal to the poll interval), so peers have the new key even if a NOTIFY was missed. Then start signing with the new key.
  3. Remove the old key once the identity-token TTL plus clock skew has passed **since it stopped signing**.
  - A second rotation within the grace drops the staged key, which never signed, and stages a fresh one. The current key keeps signing until the new grace ends.
  - The response returns the new `kid` and its `activatesAt`.
  - Activation and retirement use the injected `Clock`, so tests are deterministic.
- **Interface:** `GatewayKeyStore`, with `currentSigningKey()`, `publicJwks()` and `rotate()`.
- **Guidance for upstream verifiers** (also in the README):
  - Fetch the JWKS from a **fixed, configured URL over TLS**.
  - **Never** use a key or URL supplied inside the token (`jku`, `x5u` or `jwk` headers).
  - Cache the keys and refetch on an unknown `kid`, with rate limiting so a flood of fake `kid`s can't hammer the endpoint.
  - Java/Nimbus note: Nimbus' `DefaultJWTProcessor` can't build Ed25519 verifiers (its default verifier factory omits OKP keys because Tink is optional). Select the key from a `JWKSource` with `JWKMatcher.forJWSHeader(...)`, verify with `Ed25519Verifier`, then apply `DefaultJWTClaimsVerifier`. `src/test/java/.../support/UpstreamVerifier.java` is a working example.
- **Remaining gap:** private keys live in process memory. A KMS/HSM-held key would protect them against memory disclosure on a compromised host.

**Tests:** see [testing.md](testing.md#identity-token--jwks).

**Second hop (designed but deferred):**
- **[OAuth 2.0 Token Exchange, RFC 8693](https://datatracker.ietf.org/doc/html/rfc8693):**
  - Service A exchanges its incoming identity token at a token service for a new token with `aud=B`.
  - The new token carries `act: {sub: "service-a"}` ("A acting on behalf of Acme").
  - B authorizes against the **original customer's** rights *and* checks that A is allowed to act for customers. This defeats the confused deputy.
- **Service identity (mTLS / SPIFFE):** proves that the caller really is service A. It pairs with token exchange: mTLS says who the deputy is, and the token says whose behalf it's acting on.
